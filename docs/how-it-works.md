# 작은 모델로 Unity 코드 읽기 — 파서와 11M 모델의 역할 분담

이 글은 Unity C# 코드 해석 도구 `UnityLens`와, 그 안에서 필드 사용을 판정하는 11M 모델 `MiniUnityLLM v3.3`이 **어떻게 동작하는지**를 처음 보는 사람 기준으로 설명합니다. 숫자는 모두 실제 held-out 평가에서 나온 값입니다.

---

## 1. 문제

Unity 프로젝트를 처음 받으면 이런 질문이 생깁니다.

- 이 스크립트는 무슨 역할인가?
- 누가 누구를 상속하는가?
- `speed`는 어디서 쓰이고 어디서 바뀌는가?
- 인스펙터에 노출된 필드 중 안 쓰는 것은?

사람이 하면 몇 시간, LLM에게 통째로 던지면 그럴듯하지만 **틀린 이름**이 섞입니다. 그래서 역할을 나눴습니다.

| 주체 | 책임 | 보증 |
|---|---|---|
| 파서 | 이름·줄 번호·읽기/쓰기 | 100% (결정적) |
| 모델 | 후보 중 사용 여부 판단 | 확률적 |
| LLM | 자연어 서술 | 이름만 검증 |

핵심 원칙은 하나입니다. **사실은 파서만 만들고, 모델은 판단만 한다.**

---

## 2. UnityLens 파이프라인

```
.cs 파일
  → 렉서 (주석·문자열 제거, 토큰화)
  → 타입 선언 추출 (class / struct / enum, 베이스, 인터페이스)
  → 멤버 추출 (필드, 프로퍼티, 메서드, 속성)
  → 변수 사용 스캔 (식별자별 읽기/쓰기, 줄 번호)
  → 역할 판정 (생명주기·베이스·사용 API 기반 규칙)
  → 이슈 탐지 (파일명 불일치, 빈 생명주기, 미사용 직렬화 필드)
  → 화면 (개요 / 클래스 / 변수 추적 / 배선도 / 소스)
```

파서는 C# 전체 컴파일러가 아니라 **정적 분석에 필요한 부분집합**입니다. 대신 결과가 결정적이라, 같은 코드를 넣으면 항상 같은 줄 번호가 나옵니다.

### AI 해설 카드

파서가 만든 **팩트시트**(상속, 필드, 메서드, 읽기/쓰기, 이슈)만 LLM에 보냅니다. LLM은 아래 JSON 하나만 반환합니다.

```json
{
  "summary": "3~5문장",
  "flow": [{"field": "speed", "writes": ["Start"], "reads": ["Update"], "note": ""}],
  "risks": [{"severity": "high", "title": "...", "detail": "..."}]
}
```

화면에 그리기 전에 **식별자 가드**를 통과합니다.

- `ok` — 프로젝트 심볼 테이블에 존재
- `ext` — 스캔 범위 밖 클래스 (환각 아님)
- `bad` — 존재하지 않는 이름 (취소선 + 배지)

모델이 만든 이름을 UI가 직접 검증하므로, "그럴듯한 거짓말"이 화면에 그대로 나가지 않습니다.

## 3. 왜 모델을 따로 만들었나

처음에는 11M 모델에게 전체 해설을 생성하게 했습니다. 결과는 실패였습니다.

| 버전 | 데이터 | 상속 | 필드 재현율 |
|---|---|---|---|
| v1 (1.42M) | 합성 457 | 95.8% | 1.4% |
| v2 (11M) | 합성 9,000 | 100% (합성) / 50% (실제) | 0% (실제) |
| v3 (11M) | 실제 1,391파일 | 70% | **0%** |

모델은 `m_Staterivel`, `m_velevelevel` 같은 **존재하지 않는 이름**을 만들었습니다. 자유 생성 방식으로는 프롬프트의 이름을 정확히 복사하지 못합니다.

### 전환: 생성 → 선택

v3.2부터 구조를 바꿨습니다.

```
파서: 클래스 필드 목록(FIELDS)을 후보로 제시
모델: 후보 하나씩 "이 메서드에서 쓰였는가?" → Y / N
집계: Y가 나온 필드를 클래스 단위로 합집합
```

- 모델이 이름을 **새로 만들 필요가 없습니다** (후보는 파서가 제공).
- 출력이 단일 토큰(`Y`/`N`)이라 파싱이 필요 없습니다.
- 판정 근거를 후보별로 추적할 수 있습니다.

---

## 4. 모델 내부

| 항목 | 값 |
|---|---|
| 구조 | decoder-only Transformer |
| 파라미터 | 11.07M |
| 레이어 / 차원 / 헤드 | 6 / 384 / 6 |
| 컨텍스트 | 448 토큰 |
| 토크나이저 | byte-level BPE, vocab 700 |
| 학습 목표 | next-token cross-entropy (프롬프트 마스킹) |

### 점수 계산

프롬프트 마지막 위치에서 `Y`와 `N`의 로짓 차이를 씁니다.

```
score(field) = logit(Y) − logit(N)
선택 조건: score > 0
```

확률로 바꾸면 `sigmoid(score)`입니다. threshold를 바꾸면 정밀도/재현율 트레이드오프가 생기지만, 실측에서 최적점이 이미 0.00이었습니다.

### 학습 데이터

- 실제 GitHub Unity 코드 1,391파일에서 메서드 단위 4,187개 학습 샘플
- 각 샘플에서 (메서드, 클래스 필드) 쌍을 생성
- 양성 5,739 / 음성 19,962
- v3.4에서는 같은 클래스·다른 메서드 필드를 **하드 네거티브**로 2배 샘플링

---

## 5. 평가 방법

- 학습에 쓰지 않은 **182개 클래스**에서 100개를 평가에 사용
- 2,058개 (메서드, 필드) 쌍 / 정답 필드 489~494개
- **클래스 단위**: 여러 메서드의 선택을 합집합 → 제품 화면과 일치
- **메서드 단위**: 한 메서드 안에서 정확히 골랐는가 → 엄격한 진단

| 지표 | v3.3 |
|---|---|
| 클래스 재현율 | 74.7% |
| 클래스 정밀도 | 84.8% |
| 메서드 정밀도 | 31.9% |
| 메서드 재현율 | 73.8% |

같은 모델인데 단위에 따라 정밀도가 84.8%와 31.9%로 갈립니다. **어떤 지표를 제품 지표로 삼는지가 설계 결정**입니다.

---

## 6. 오탐은 어디서 나오는가

2,058쌍을 분석한 결과입니다.

| 항목 | 값 |
|---|---|
| AUC | 0.680 |
| 오탐 | 726 |
| 그중 같은 클래스·다른 메서드 필드 | **575 (79%)** |
| 본문 등장 필드 선택 정밀도 | 93.2% |
| 본문 미등장 필드 선택 정밀도 | 0.0% |

모델은 "이 필드가 클래스에 속한다"까지는 알지만, "이 메서드에서 쓰였는가"는 구분하지 못합니다. 344개 메서드 중 149개(43%)가 후보를 전부 선택했습니다.

### 후보 필터는 왜 실패했나

본문에 등장하는 필드만 후보로 주면 정밀도는 84.7% → 88.9%로 올랐지만, 재현율이 74.8% → 42.5%로 무너졌습니다. 실제 사용 필드가 프로퍼티·콜백·인자 전달로 쓰이면 본문에 이름이 등장하지 않기 때문입니다. F1은 0.795 → 0.575.

### v3.4도 실패했다

`IN_CODE` 피처와 하드 네거티브를 넣은 v3.4는 정밀도 86.1%, 재현율 72.0%로 F1이 0.784였습니다. 정밀도는 올랐지만 재현율 손실이 더 커 **채택하지 않았습니다.**

## 7. 한계

- **11M의 표현력** — 메서드 문맥과 필드 사용을 구분하기에 작습니다.
- **평가셋 100클래스** — 1건이 약 0.2pp, 여전히 작습니다.
- **파서의 문자열 기반 후보** — 리플렉션·문자열 접근은 회복 불가.
- **LLM 해설 경로** — 실제 엔드포인트 왕복은 아직 검증하지 못했습니다(스키마·가드만 테스트).
- **역할 판정** — 규칙 기반이라 프로젝트 관례에 따라 흔들립니다.

## 요약

- 정확한 사실은 **파서**가 만든다.
- 모델은 **후보를 고르는 판단**만 한다. 그래서 이름을 지어낼 수 없다.
- 해설은 LLM이 하되, **이름은 파서가 검증**한다.
- 현재 필드 선택: 클래스 재현율 74.7%, 정밀도 84.8% (100클래스).
- 메서드 단위 정밀도 31.9%는 남은 과제이며, 후보 필터로는 해결되지 않는다.
